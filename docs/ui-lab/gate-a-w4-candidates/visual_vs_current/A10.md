# A10 — Assistant Coach structured action: current-state comparison

**Coach question:** Can Assistant Coach propose a specific lineup change I can inspect and apply
without leaving Match Details, and does it honestly refuse to apply when the plan has moved on or
when it has nothing to propose?

## Current-state baseline

`NO_BASELINE_CAPABILITY`. Verified by direct read (`CURRENT_STATE_AUDIT.md` item 5):
`src/lib/ai/presentation/planned-match-advisor.ts`'s `PlannedMatchAdvisorViewModel` only ever
carries free-text `insights` (`title`/`body`/`kind`/`evidenceRefs`) — there is no structured,
applicable lineup-assignment payload anywhere in current production. The closest real behaviour is
A07's plain "assign an already-in-squad candidate" editor, which has no evidence/rationale/
limitations/expected-consequences disclosure at all, because its candidate is a manual choice, not
an AI proposal.

## A10-review-alternative-success

- **Current-state deficiency:** no equivalent exists to compare against.
- **Proposed difference:** the SAME desktop-inspector/mobile-sheet chrome as A07, but the body is a
  structured proposal with cited evidence, a rationale distinct from the evidence, and disclosed
  limitations — the coach can tell exactly what is known versus inferred before applying.
- **User-impact proof:** `proposal-evidence-count` and the limitation list are both visible before
  any selection is made; the diff preview and "advisory only, not a guaranteed outcome" disclaimer
  appear only once selected.
- **Accepted trade-off:** this is a UI-Lab-only design candidate for a capability that does not yet
  exist in production — see `BLOCKERS.md` W4-BLK-03/W4-BLK-04.

## A10-stale-proposal-blocked

- **Current-state deficiency:** no equivalent exists — there is no production concept of a
  structured proposal going stale, because there is no structured proposal yet.
- **Proposed difference:** the proposal is fully inspectable (evidence, rationale, diff) but no
  Apply affordance renders at all — verified by test:
  `screen.queryByRole("button", { name: "Apply proposal" })` is `null`.
- **User-impact proof:** a reviewer can confirm staleness is detected before any submit, not
  discovered as a server conflict after confirming — the exact distinction
  `12_ACTION_OWNERSHIP_AND_GUARDRAILS.md` draws between "reject before render" and "reject on
  apply".
- **Accepted trade-off:** none specific to this case.

## A10-disabled-or-failed

- **Current-state deficiency:** no equivalent exists.
- **Proposed difference:** "Review lineup" stays a reachable, enabled action even with nothing to
  propose; the honest reason explicitly points back to manual editing as unaffected.
- **User-impact proof:** `screen.queryByTestId("lineup-proposal-card")` is `null` — no fabricated
  proposal renders merely to have something to show.
- **Accepted trade-off:** none specific to this case.

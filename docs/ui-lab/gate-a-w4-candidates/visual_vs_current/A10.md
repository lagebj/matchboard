# A10 — Assistant Coach structured action: current-state comparison

**Coach question:** Can Assistant Coach propose a specific lineup change I can inspect and apply
without leaving Match Details, and does it honestly refuse to apply when the plan has moved on or
when it has nothing to propose?

## Current-state baseline

`NO_BASELINE_CAPABILITY`. Verified by direct read (`CURRENT_STATE_AUDIT.md` item 5):
`src/lib/ai/presentation/planned-match-advisor.ts`'s `PlannedMatchAdvisorViewModel` only ever
carries free-text `insights` (`title`/`body`/`kind`/`evidenceRefs`) — there is no structured,
applicable lineup-assignment payload anywhere in current production. The closest real behaviour is
A07's plain "assign an already-in-squad candidate" editor, which has no evidence/rationale/
limitations/expected-consequences disclosure at all, because its candidate is a manual choice, not
an AI proposal.

## A10-review-alternative-success

- **Current-state deficiency:** no equivalent exists to compare against.
- **Proposed difference:** the SAME desktop-inspector/mobile-sheet chrome as A07, but the body is a
  CONTRACT-VALIDATED proposal (`lineup-proposal-contract.ts`'s `validateLineupProposal`, run before
  anything renders as actionable) with per-source inspectable evidence, a rationale distinct from
  the evidence, and disclosed limitations — the coach can tell exactly what is known versus
  inferred before applying. Reopening after a successful apply shows an honest "Already applied
  (simulated)" state, not a freshly re-actionable proposal (independent review finding R4).
- **User-impact proof:** the `proposal-evidence-inspector` lists each source's kind (recorded
  match fact / coach-declared / development evidence), coverage, and what specifically it supports
  — not a bare count — before any selection is made, as a sibling of (never nested inside) the
  separate "Select proposal" button (round-2 finding N2, verified by a DOM-containment test and a
  structural "no `<details>` inside a `<button>`" assertion); the diff preview names the actual
  proposed player ("RCM: Empty → Tobias", round-2 finding N3) with its own "Draft, not yet
  applied." status line, and "advisory only, not a guaranteed outcome" disclaimer appear only once
  selected; `Discard draft` is unavailable while `PENDING` (round-1 finding R3); the authoritative
  pitch is never mutated a second time by reopening (round-1 finding R4, verified by test).
  Validation resolves the occupant of the proposal's OWN exact target slot from the same
  authoritative projection the pitch renders from, not one hardcoded slot (round-2 finding N1,
  verified by a dedicated regression test reproducing the exact GK-vs-RCM confusion the review
  reported).
- **Accepted trade-off:** this is a UI-Lab-only design candidate for a capability that does not yet
  exist in production — see `BLOCKERS.md` W4-BLK-03/W4-BLK-04. The validation contract checks
  structure/scope only, never permission or eligibility — see `ACTION_OWNERSHIP.md`'s "No second
  rules engine" disclosure.

## A10-stale-proposal-blocked

- **Current-state deficiency:** no equivalent exists — there is no production concept of a
  structured proposal going stale, because there is no structured proposal yet.
- **Proposed difference:** `validateLineupProposal` itself returns `applicability: "STALE"` for
  this fixture (a structural property, not a UI-only label) — the proposal's rationale and
  evidence stay fully inspectable, but no Select/Apply row renders at all — verified by test:
  `screen.queryByTestId("lineup-proposal-row")` and `screen.queryByRole("button", { name: "Apply
  proposal" })` are both `null`.
- **User-impact proof:** a reviewer can confirm staleness is detected before any submit, not
  discovered as a server conflict after confirming — the exact distinction
  `12_ACTION_OWNERSHIP_AND_GUARDRAILS.md` draws between "reject before render" and "reject on
  apply". The 45-case `lineup-proposal-contract.test.ts` suite (round 2: up from 17) proves this is
  one of 14 distinct rejection codes plus the separate stale-but-inspectable blocking outcome, not
  an ad hoc special case — including malformed-payload rejection that never throws (round-2 finding
  N4).
- **Accepted trade-off:** none specific to this case.

## A10-disabled-or-failed

- **Current-state deficiency:** no equivalent exists.
- **Proposed difference:** "Review lineup" stays a reachable, enabled action even with nothing to
  propose; the honest reason explicitly points back to manual editing as unaffected.
- **User-impact proof:** `screen.queryByTestId("lineup-proposal-card")` is `null` — no fabricated
  proposal renders merely to have something to show.
- **Accepted trade-off:** none specific to this case.

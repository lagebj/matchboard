# A11 — Qualitative evidence + mutation: current-state comparison

**Coach question:** When I write a free-text note, can I see exactly what was structured from my
own words (and nothing more); and when a profile change is proposed, can I see the before/after
and evidence, and explicitly accept, reject, or defer it — without the system silently deciding
for me?

## Current-state baseline

`PARTIAL_BASELINE`. `src/lib/evidence/qualitative-evidence-extraction-contract.ts` is a real,
already-shipped schema/validation module (ADR-0152) — this candidate's extraction scenario reuses
it directly rather than inventing a parallel shape. There is, however, no current production UI
that shows the coach their own extracted observations side-by-side with the original note; the
extraction pipeline's output is consumed internally, not surfaced for direct review in this form.
For profile mutation: `src/lib/evidence/player-evidence-service.ts` is real and already applies
numerical attribute proposals **automatically**, and `docs/adr/0139-evolving-player-position-
model.md` (Accepted) auto-promotes primary position **without** coach approval — the opposite of
what A11's guarded-review candidate demonstrates. See `BLOCKERS.md` W4-BLK-09.

## A11-coach-text-and-parsed-evidence

- **Current-state deficiency:** no current production surface shows the coach their own note next
  to its parsed observations for direct review.
- **Proposed difference:** the original note renders immutable and attributed; each parsed
  observation is validated against the real extraction schema and labelled explicit/tentative, with
  its phase and polarity, never silently resolving an uncertain claim.
- **User-impact proof:** `safeParseExtractionResponse`/`validateExtractionSemantics` (the real
  functions) both accept this fixture's data in its own test — the displayed observations are not
  hand-waved shapes.
- **Accepted trade-off:** the extraction call itself is never made; this is a pre-validated fixture
  standing in for its output.

## A11-profile-change-review-guarded / A11-profile-change-review-rejected

- **Current-state deficiency:** current production (`ADR-0139`, already shipped) auto-promotes
  primary position without any coach-facing review step at all — this candidate demonstrates the
  opposite: an explicit before/after review with Accept/Reject/Defer, before anything changes.
- **Proposed difference:** the proposal states its evidence and an explicitly disclosed
  hypothetical materiality threshold (never an approved number); accepting, rejecting, or deferring
  are three distinct, equally first-class outcomes, not a binary apply/cancel.
- **User-impact proof:** `profile-change-outcome` reads "No real provider or database write
  occurred" in every outcome, and the declared primary position is never altered in any real
  Matchboard record by this candidate.
- **Accepted trade-off:** this directly contradicts `ADR-0139`'s current shipped behaviour by
  design — it demonstrates the v0.5.4 product target, not a claim that current production already
  works this way. Reconciling the two is a separate, deliberate domain decision (`BLOCKERS.md`
  W4-BLK-09), not something this UI-Lab candidate resolves.

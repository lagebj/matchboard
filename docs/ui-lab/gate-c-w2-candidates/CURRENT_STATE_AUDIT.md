# Gate C W2 — Current Production State Audit

Classification per the brief: `CONFIRMS_SHIPPED_BASELINE`, `PROPOSED_REFINEMENT`, `MISSING_CAPABILITY`, `BLOCKED_BY_SOURCE_OR_AUTHORITY`.

This document covers the initial implementation and both subsequent independent-review remediation passes (findings P1-01 through P1-07, then a second pass's four further findings — see `REVIEW_RECORD.md` for the full disposition). ## 2. Eligible-player coverage denominator (C04)

**MISSING_CAPABILITY, now fixed.** `computeRoundPlanIntegrity()` already returns `coverage: {eligibleAvailablePlayerCount, assignedEligibleAvailablePlayerCount, unassignedEligibleAvailablePlayerIds}` (`compute-plan-integrity.ts:528-532`) — but `page.tsx` never read `integrity.coverage`, and `round-board.tsx` separately recomputed its own "available players" count client-side (`unassignedPlayers.length`), and that recomputed value was passed into a `RoundBoardAdapterInput.availablePlayerCount` field the adapter never actually consumed (dead parameter — confirmed by reading `buildRoundBoardViewModel`'s full body). No canonical coverage number reached the UI at all.

**Fix** (this PR): `page.tsx` now forwards `integrity.coverage` to `<RoundBoard coverage={...}>`; `round-board.tsx` passes it through to `buildRoundBoardViewModel` as a new `eligibleCoverage` field on `RoundBoardSummary`; `RoundStatusStrip` renders it as its own tile, labeled "Eligible players with an opportunity ({pct}%)", explicitly distinct from "Opportunities planned ({pct}%)" (squad placements). The dead `availablePlayerCount` parameter was removed rather than left alongside the real fix.

**Naming nuance (disclosed, not changed):** `coverage.eligibleAvailablePlayerCount`/`assignedEligibleAvailablePlayerCount` are **not** availability-filtered despite the name — they count all eligible active players (active, not removed, core team has a playable fixture this round) regardless of current availability status. Only the separate `unassignedEligibleAvailablePlayerIds` list is availability-filtered. See `OPPORTUNITY_COVERAGE_SEMANTICS.md`.

## 3. Closed-destination assignment gap (C05) — DESTINATION *and* SOURCE

**MISSING_CAPABILITY (a real defect), now fixed, twice.** First pass: `handleMatrixToggle` already checked `target.isFinalized` before assigning (`round-board.tsx`, pre-existing). `handleAssignSuggestion` — the suggestion-card/inspector/sheet commit path — had no equivalent check, and `buildAssignmentContext`'s caller offered every other match as a destination regardless of `isFinalized`. A closed match could render as an assignable suggestion and accept an assignment from the inspector or mobile sheet.

Independent review (P1-03) found the first pass's fix was destination-only: `movePlayerToMatch` removed a player from their `fromMatchId` unconditionally once the add succeeded, so a player currently on a CLOSED match could still be removed from it as a side effect of the matrix toggling a *different*, open match's cell for them, or of a suggestion-card assignment into a genuinely open destination (the outer guard in `handleAssignSuggestion` only ever checked the *target*).

**Fix** (remediation pass): `movePlayerToMatch` is now the single place both boundaries are checked, before any action is taken — it looks up both `fromMatchId` and `targetMatchId`'s `isFinalized` and returns a rejection outcome (see item 8 below) without calling any action if either is closed. Found and fixed during this remediation's own test-writing (beyond the review's literal wording): the suggestion-card/inspector path also stopped *offering* a destination at all once the selected player's own current match is closed — showing a suggestion that is guaranteed to fail the moment it's tapped is the same class of defect as P1-01's false Resolve button, so `openDestinationMatches` is now empty (with `closedNotice` explaining why) whenever `selectedPlayerSourceClosed` is true, not just when every *other* match happens to be closed.

A second independent review found the desktop Move picker (`MoveDestinationList`, a sibling path to the suggestion card, reached from the inspector's "Move to..." control) had never had this filter applied at all — it listed every other match regardless of `isFinalized`. **Fix** (second remediation pass): `otherMatchesForPicker` is filtered to `moveDestinations` (`!isFinalized`) before rendering; `otherMatchesExistButClosed` distinguishes "no other matches exist" from "other matches exist, but closed" in the empty state.

## 4. `RoundBoardRail`'s `onResolve` button — now gated per item, not just provided unconditionally

**MISSING_CAPABILITY (a real defect, found by independent review as P1-01), now fixed.** The first pass judged `onResolve` itself safe because it only opens the inspector (selection, not a mutation) — true, but independent review correctly identified that the Resolve *button itself* rendering unconditionally is still a false affordance for a historical, unactionable item: a coach has no way to tell, before clicking, whether anything will actually be reachable.

**Fix:** `RoundBoardAttentionItem` gained a `resolvable: boolean` field, computed once in `buildRoundBoardViewModel` (the production adapter) from the same per-match `isFinalized` data already passed in — never a second derivation, and never the round-level boundary alone (a mixed round has both open and closed matches). `RoundBoardRail` renders the Resolve control only when `onResolve && item.resolvable`.

A second independent review found this first-pass `resolvable` computation itself had a gap: `isResolvable` checked only whether *some other* match was open, never whether the signal's own player's *current* match had itself closed. A player assigned to a CLOSED match was therefore still marked `resolvable: true` purely because a different match happened to be open — the exact false-affordance class P1-01 was supposed to eliminate, just one level deeper. **Fix (second remediation pass):** `isResolvable` now resolves the player's current match via `matchIdByPlayerId` first and returns `false` immediately if that match is not open, before considering any other match at all.

The routing logic in `round-board.tsx`'s `onResolve` handler was also extended: a player-specific item selects that player (unchanged); a match-specific item with no single player routes into that match's own context in the compact composition. This originally claimed to be "a no-op on desktop, where every lane is already visible" — a second independent review found that claim was simply wrong: on desktop it updated only mobile-only state, so clicking Resolve for a match-specific item visibly did nothing at all. **Fix (second remediation pass):** a new `handleResolveMatch` callback also scrolls the real match lane (`[data-drop-match]`) into view on desktop and moves focus to a real interactive control inside it (the lane's first "Select" button, falling back to the lane itself only if no such button exists). An item with neither identifier, or whose only possible target is closed, is never resolvable at all (fail-safe, per the brief's own instruction not to guess).

## 5. Allocation matrix is never reachable once the round-level boundary is closed

**CONFIRMS_SHIPPED_BASELINE, with a worth-noting consequence (not a defect).** The Board/Allocation toggle only renders inside `{planningBoundaryOpen && (...)}`, and round-level `planningBoundaryOpen` is only `true` when every match in the round is open (`isMatchRoundPlanningEditable`, ADR-0109). Consequently, the Allocation matrix is structurally unreachable in any round with even one closed match — there is no "reachable but per-cell-guarded" matrix state to exercise for a mixed or fully-closed round. `handleMatrixToggle`'s own `target.isFinalized` check is therefore unreachable dead code in production today (it can only matter if a future change decouples the toggle's visibility from the round-level gate). Not fixed — removing defensive code that is harmless, or changing the toggle's gating, is outside this wave's bounded scope and not required by any C04-C06 acceptance question.

## 6. Position vocabulary in Round Board (C06)

**BLOCKED_BY_SOURCE_OR_AUTHORITY.** Direct audit of `prisma/schema.prisma`, `src/domain/positions/`, and every repo-wide consumer of `CANONICAL_TACTICAL_POSITIONS`/`SOURCE_ROLES` confirms:

- `Selection` (the model Round Board mutates) has a `role: SelectionRole` field — a planning *category* (CORE/SUPPORT/BACKFILL/DEVELOPMENT/CONFIDENCE_REBUILD/...), not a position. No position field exists on `Selection` at all.
- `Player.primaryPosition`/`secondaryPosition`/`tertiaryPosition` are unconstrained free-text strings — never validated against either vocabulary.
- The 24-code `CANONICAL_TACTICAL_POSITIONS` vocabulary is genuinely owned by a *different* feature: the Lineup/Formation editor (`FormationSlot.gridX/gridY` → `canonicalPositionForCell`, `src/app/(app)/matches/[matchId]/page.tsx`, `src/components/formations/`). It is also written as live-match evidence (`ActualPositionInterval.position`, via `live-match-client.tsx`'s position-correction flow) — a different concept again (realised evidence, not a plan).
- `projectToBaseRole` (`src/domain/positions/compatibility-projection.ts`) is the real ADR-0154 projection, mapping 24-code → 12-code `ExactRole` + side. It has zero callers anywhere in the Round Board component tree, view-model, or adapter.

Round Board's assignment is, and has always been, player×match only (`AllocationMatrixRow.assignments: Record<matchId, boolean>`). There is no exact tactical-position data to "retain precision" on within this surface — fabricating one here would be exactly the "invent a new tactical placement system" the brief forbids.

**Disclosure, not fabrication** (this PR): the assignment inspector continues to show `Player.primaryPosition` exactly as production already did (free text, unchanged). A new, small, honest addition — a "View exact position in Lineup →" link from the inspector to the selected player's current match (`/matches/{matchId}`), shown only once a match assignment exists — is the "correct canonical context or navigation" the brief explicitly allows in place of fabricated precision. See `POSITION_VOCABULARY_AND_PRECISION.md`.

## 7. Command/presentation boundary for UI Lab — incomplete on the first pass

**MISSING_CAPABILITY, now built, then found incomplete, then completed.** First pass: `round-board.tsx` imported five server actions directly at module scope, with no way to inject a safe stand-in for UI Lab. A new `RoundBoardCommands` optional prop (default: the same five real actions, so production — which never passes it — is byte-for-byte unchanged) lets `RoundBoardFixtureHarness` supply deterministic in-memory responses.

Independent review (P1-06) found this boundary incomplete: `MatchLane` renders `CoachingIntentSelector` for every open match, and that component dynamically imports its *own* real server actions (`setCoachingIntentAction`/`removeCoachingIntentAction`) entirely outside `RoundBoardCommands` — a UI Lab fixture could still reach a real mutation with a synthetic match id through it.

**Fix:** `CoachingIntentSelector` gained two optional command props (`setCoachingIntentCommand`/`removeCoachingIntentCommand`), defaulting to the same real dynamic imports when omitted — every *other* caller of this shared, widely-used component is unaffected. `RoundBoardCommands` gained matching `setCoachingIntent`/`removeCoachingIntent` entries, threaded through `MatchLane`'s new `coachingIntentCommands` prop. The audit also covered Clear/Regenerate, which the first pass had wired to no-ops that returned success despite doing nothing fixture-local — now disabled outright in UI Lab (`disableClearAndRegenerate`, a new `RoundBoardProps` flag) with an explanatory `title`, since no deterministic fixture behavior exists for either and a no-op "success" would mislead.

## 8. `movePlayerToMatch` returned void — a rejection was indistinguishable from a success

**MISSING_CAPABILITY (P1-05), now fixed.** Every caller called `movePlayerToMatch` and then unconditionally refreshed/closed, regardless of whether `addPlayerToMatchAction`/`removePlayerFromMatchAction` actually succeeded. A real server-side rejection produced no visible feedback — not a false success exactly, but an unexplained silent no-op, and (combined with item 3's gap) a path where a genuinely rejected move's sheet closed as if it had worked.

**Fix:** `movePlayerToMatch` now returns a `MoveOutcome` (`{status: "success"} | {status: "rejected", reason} | {status: "error", reason}`). Every caller (drag/drop, touch-drag, the matrix, the non-drag Move picker, the suggestion card) branches on it: only a genuine success triggers `router.refresh()`/closes the sheet; a rejection or error sets a shared `assignmentError` shown inline in the inspector/sheet (when a player is selected — the panel that actually has the context) or in a dismissible top-level banner otherwise. The add-then-remove sequence's own genuine partial-completion risk (add succeeds, the subsequent remove fails) is surfaced as an explicit error rather than silently treated as a success — not "solved" with a transaction redesign, which the brief explicitly excludes from this wave.

## 9. Dropped signal identity between the plan-integrity engine and the board

**MISSING_CAPABILITY (P1-04), now fixed.** `page.tsx`'s mapping from `PlanIntegritySignal` to the board's `warnings` prop dropped `playerId`, `matchId`, and the signal's own `idempotencyKey` entirely — `round-board.tsx`'s `attentionItems` then hardcoded `matchId: null` and derived `id` from an array index. This silently broke match-specific Resolve routing (there was never a `matchId` to route with) and made per-item resolvability impossible to compute correctly for anything that wasn't a UI-Lab fixture hand-authoring these fields directly — which is exactly why this gap never surfaced in the first pass's own fixtures.

**Fix:** `page.tsx` now carries `playerId`/`matchId`/`idempotencyKey` through (resolving `playerName` from data it already fetches — no new query), and `attentionItems` uses them instead of `null`/an index-derived id.

## 10. C05's historical warning didn't match the engine's own rules (fixture integrity, not production code)

**Fixture defect (P1-02), now fixed.** The original C05 fixture asserted a retained `SELECTED_PLAYER_UNAVAILABLE` warning on a finalized selection — `compute-plan-integrity.ts` only ever generates that rule for `DRAFT` selections, so the fixture was claiming a canonical signal the real engine could never actually produce for a closed match. Replaced with `SQUAD_BELOW_MINIMUM`, which the engine evaluates across both draft and finalized selections for every non-cancelled match regardless of planning boundary — a signal that genuinely can, and does in production, outlive the match's closure. See `DATA_TRUTH_AND_FIXTURES.md` for the corrected fixture's exact numbers.

## 11. Mixed-boundary banner claimed every match was closed when only some were

**MISSING_CAPABILITY (a real defect, found by a second independent review), now fixed.** `isMatchRoundPlanningEditable()`'s round-level gate is deliberately all-or-nothing (item 1's baseline, ADR-0109) — one closed match is enough to make `planningBoundaryOpen` false even if every other match remains open. The single "Planning closed" banner that fired on `!planningBoundaryOpen` narrated this as if *every* match had closed, which is simply false for a mixed round like C05's own primary fixture (Rød closed, Hvit open).

**Fix:** new `closedMatchCount`/`allMatchesClosed`/`mixedPlanningBoundary` derived state in `round-board.tsx` splits the banner into three mutually exclusive branches: mixed ("Round-wide planning locked" / "Some matches have closed..."), fully closed ("Planning closed" / "All matches have passed..."), and a safe fallback for the structurally-impossible-in-production empty-round case that avoids claiming anything closed at all. This is a wording/derived-state correction only — the underlying all-or-nothing round-level semantics are unchanged and still correctly drive Regenerate/Clear's visibility.

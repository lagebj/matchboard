# Gate C W2 — Review Record

## Summary

Three candidates (C04, C05, C06 — plus a dedicated denied-assignment route for C06) built against the real, unmodified `RoundBoard` production component tree, via a fixture command boundary that never touches a live database mutation. The initial implementation found and fixed two real production defects (eligible-coverage data never surfaced; a closed match could still accept an assignment from the inspector/sheet) and correctly disclosed C06's position-precision gap as `BLOCKED_BY_SOURCE_OR_AUTHORITY` rather than fabricating it.

An independent review of that implementation found seven further findings (P1-01 through P1-07). All seven were fixed in that pass, verified with real browser tests in addition to component tests, and documented below finding-by-finding.

A second independent review (of HEAD `af686e3cd8cf0a0633f18d931bb47bf7a6eca590`) found that two of those fixes (P1-01, P1-03) were incomplete in a specific way neither pass's original tests exercised, plus two further defects. All four are fixed in this second remediation pass — see "Second remediation pass findings" below.

A third independent review (of HEAD `c03f148e4d4e6a7448fc7a375509043e0d7c5040`) found that the second pass's own Resolve fixes were still not enough: scrolling to and focusing a control is navigation, not a genuine correction path, and the player-specific `resolvable` check still didn't account for the warning's own owning match independently of the player's current one. Three further findings, all fixed — see "Third remediation pass findings" below.

## Second remediation pass findings (reviewed HEAD `af686e3cd8cf0a0633f18d931bb47bf7a6eca590`)

| Finding | Root cause | Fix | Tests |
|---|---|---|---|
| Resolve eligibility re-opened — a player-specific warning on a now-CLOSED match could still show Resolve | `isResolvable` in the production adapter checked only whether *some other* match was still open; it never checked whether the signal's own player was currently assigned to a match that had itself closed | `isResolvable` now resolves the player's current match via `matchIdByPlayerId`, and returns `false` immediately if that match exists and is not open, before considering any other match | `round-board-production-adapter.test.ts` — full decision matrix rewritten: unassigned+open-exists→true, assigned-to-open+another-open-exists→true, **assigned-to-closed+another-open-exists→false** (the flipped case), assigned-to-closed+all-closed→false, unassigned+all-closed→false, match-specific-open→true, match-specific-closed→false, identity-less→false |
| Match-specific Resolve had no effective desktop behavior | `onResolve` for a match-only attention item only updated mobile-only state (`setMobileMatchId`/`setMobileMode`); on desktop, where that state renders nothing, clicking Resolve visibly did nothing | New `handleResolveMatch` callback also scrolls the real match lane (`[data-drop-match]`) into view and moves focus to a real interactive control inside it (the lane's first "Select" button, falling back to a focusable lane container only if the lane has no such button) | `round-board.test.tsx` — two new tests (scroll+focus-on-first-select-button; scroll+focus-on-lane fallback when no select button exists); `ui-lab-gate-c.spec.ts` — real-Chromium test against the new `c05-planning-closed/open-match-warning` route asserting the lane scrolls into view and a real "Select" button receives focus |
| Mixed-boundary banner said every match was closed when only some were | The single "Planning closed" banner branch fired whenever `!planningBoundaryOpen`, regardless of how many matches had actually closed | New `closedMatchCount`/`allMatchesClosed`/`mixedPlanningBoundary` derived state splits the banner into three mutually exclusive branches: fully mixed ("Round-wide planning locked" / "Some matches have closed..."), fully closed ("Planning closed" / "All matches have passed..."), and the empty-round edge case (falls back to "This round's planning boundary is closed." rather than falsely claiming matches closed) | `round-board.test.tsx` — three new tests (mixed, fully-closed, empty-round fallback); `ui-lab-gate-c.spec.ts`'s existing C05 banner assertion corrected from the old single-branch wording to assert both the mixed-specific heading and body text, since C05's fixture is genuinely mixed (Rød closed, Hvit open), not fully closed |
| Desktop Move picker still offered closed destinations | `MoveDestinationList`'s candidate list was every other match, with no `isFinalized` filter — unlike the suggestion-card path, which already excluded closed matches | `otherMatchesForPicker` (every other match) is now filtered to `moveDestinations` (`!isFinalized`) before rendering; a new `otherMatchesExistButClosed` flag distinguishes "no other matches exist" from "other matches exist, but their planning is closed" so the empty state is never misleading | `round-board.test.tsx` — three new tests (closed destination excluded, empty-vs-closed messaging distinguished, a genuinely open destination is still offered); `ui-lab-gate-c.spec.ts` — real-Chromium test on C05 asserting the closed match is absent from the Move picker and the closed-explanation text renders |

## Found and fixed while generating this pass's own real CI attestation evidence

- **The real CI run initially crashed, not merely failed.** The first push of this pass's fixes crashed the entire `ui-lab-visual-review.yml` capture job with an uncaught `TimeoutError`: the new `move-picker-excludes-closed` capture-script interaction clicked the chip's "Move Markus to..." button unconditionally, but that button is genuinely absent from the accessibility tree below the desktop breakpoint (CSS-hidden via `hidden medium:grid`), so `getByRole` never found it on the mobile viewport variant and the 30s timeout aborted the whole run. Fixed with an `isVisible()` guard (same precedent as the existing Allocation-toggle interaction); verified locally against a real Chromium instance across all five viewport widths the scenario captures before re-pushing. The corrected run completed green (98 Gate C Playwright tests, capture job success).
- **A pre-existing documentation inaccuracy from the first remediation pass.** Several documents (`BLOCKERS_AND_KNOWN_LIMITATIONS.md`, `SCENARIO_REGISTER.md`, `CHANGED_FILES.md`, this document's own P1-07 row, `candidate_manifest.json`) claimed the capture script registered "all four" C04-C06 routes, including the dedicated denied-assignment sub-route. Direct inspection of the real CI artifact (no `gate-c-w2-c06-dense-allocation-denied-assignment-*.png` files exist in it) showed this was false — only C04/C05/C06's three primary routes were ever capture-registered; the denied-assignment behavior is real-browser-tested, just via a dedicated Playwright acceptance test (`ui-lab-gate-c.spec.ts`), not a screenshot. Corrected in place rather than left standing, per this pass's own instruction not to let evidence claims outrun what was actually verified.

## Third remediation pass findings (reviewed HEAD `c03f148e4d4e6a7448fc7a375509043e0d7c5040`)

| Finding | Root cause | Fix | Tests |
|---|---|---|---|
| P1 — match-specific Resolve didn't reach an actionable correction | The second pass's `handleResolveMatch` scrolled to and focused the resolved match's first ASSIGNED player's own "Select" control. But that player's own current match is always excluded as a destination for *themselves* (the closed/open-boundary filtering already in place), so the resulting workflow could never add anyone to a squad that is short — scrolling to the correct match is navigation, not resolution | Resolve now directs the coach at the existing "Available" (unassigned) list instead — the same list that already feeds the real select → suggest → assign workflow. A new `pendingAssignmentTarget` presentation state (`{matchId, signalId}`) retains the target through candidate selection; the existing matching suggestion (if reachable) is marked the dominant, recommended one via the pre-existing `isRecommended` flag, with a "Resolving: {warning}" note shown above it. No new eligibility algorithm, no auto-assignment — the coach still explicitly picks a candidate and commits via the existing `movePlayerToMatch` command. When no eligible candidate exists at all, a dedicated notice explains the condition rather than focusing a misleading control | `round-board-production-adapter.test.ts` has no change here (this is presentation-only); `round-board.test.tsx` — 4 new tests (no-candidate explanation, candidate focused in Available, the override directs at the actual shortage match over the generic recommendation, committing clears the pending target); `round-board.test.tsx` P3 describe block — 2 more mobile-specific tests; `e2e/ui-lab-gate-c.spec.ts` — 4 new real-Chromium tests (desktop focus, mobile focus + URL state, a full commit sequence with truthful squad-count updates, a rejection sequence) |
| P2 — Resolve eligibility didn't respect the warning's own owning match | `isResolvable`'s player-specific branch checked the player's *current* match's boundary, but never the signal's own `matchId` (the warning's owning match) independently — a warning naming a CLOSED match could be marked resolvable purely because the player was unassigned, or assigned to a different, open match | A new early check — `if (signal.matchId && !isMatchOpen(signal.matchId)) return false;` — runs before the player-specific branch, decisive on its own regardless of the player's current assignment | `round-board-production-adapter.test.ts` — 6 new tests covering the full ownership × player-state matrix from the brief, including the two genuinely new cases (closed-owner + unassigned-elsewhere-open, closed-owner + assigned-to-a-different-open-match) |
| P3 — mobile Resolve could focus a CSS-hidden desktop control | `handleResolveMatch`'s focus-target query (`document.querySelectorAll("[data-drop-match]")`, and the new Available-column query) selected the first DOM match regardless of which composition's CSS currently hides it — both the desktop grid and the compact composition render every match/Available-column simultaneously | A new `isMobileCompositionVisible` (`useMediaQuery("(max-width: 599px)")`) — the literal CSS breakpoint boundary, deliberately distinct from the pre-existing `isCompactViewport` (839px), which only chooses dialog *style* and would be wrong in the 600-839px range — picks between two new explicit, stable, component-owned containers (`[data-desktop-board]` / `[data-mobile-board]`) to scope every focus/scroll query within, never DOM order. The mobile-state sync itself (`mobileMode`/`mobileMatchId`/URL) stays unconditional (harmless when hidden, matching the prior pass's own behavior) — only the FOCUS target needed to become viewport-scoped | `round-board.test.tsx` — the P3 describe block's 2 tests (mock `(max-width: 599px)` true, assert focus lands in `[data-mobile-board]`, never the desktop one); `e2e/ui-lab-gate-c.spec.ts` — a real 390px-viewport Chromium test asserting URL state, the real focused control, and `[data-desktop-board]` being hidden |

No finding required deviating from the brief's hard constraints in this pass either: no schema change, no new selection engine, no new eligibility algorithm, no new planning-boundary authority, no server-authorization change, and Round Board was not redesigned — the match-targeted workflow reuses the existing player-selection, suggestion, and `movePlayerToMatch` machinery throughout.

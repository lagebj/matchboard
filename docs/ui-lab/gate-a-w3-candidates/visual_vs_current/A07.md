# A07 — Match Details edit lineup: current-state comparison (XR-V01, XR-I01)

**Coach question:** Can I edit this match's lineup, see exactly what changed, and recover cleanly
from a denial/conflict/closed-boundary/accidental-close — all without leaving Match Details?

## Current-state baseline

Production's `MatchTacticsPanel` (`src/components/matches/match-tactics-panel.tsx`) IS the real,
shipped, in-context lineup editor — confirmed by direct read: it already stays inside Match
Details, already uses the real `TouchlinePlanningPitch`, and already has an "Add player" entry
point. It is **not usable as this candidate's literal baseline component** because it is
self-fetching (own data hooks, own mutation calls) and not fixture-injectable, per the bundle's own
`BLK-01` — so this candidate builds an isolated, dev-only presentation (`lineup-slot-editor.tsx`)
from the same real shared primitives (`TouchlinePlanningPitch`, `primaryDisplayCellFor`,
`buildPlanningPitchSlotsFromFormationSlots`) instead. The comparison below is therefore against
what the shipped panel visibly does NOT yet show for a save attempt, not against an absent
capability.

## A07-S1/S2 — open, select, preview, confirm, saved

- **Current-state deficiency:** the shipped panel's `assignPlayerToSlot` action has no visible
  pending/saved feedback sequence rendered as a distinct UI state in the panel itself (confirmed by
  read: it calls the server action and relies on standard revalidation, with no explicit
  "Saving…"/"Saved (simulated)" banner sequence).
- **Proposed difference:** an explicit, inspectable state sequence — open → select candidate →
  diff preview ("RCM: Empty → Tobias — draft, not yet saved") → `PENDING` (fixture-simulation gate)
  → "Saved (simulated)", with the real pitch re-rendering the new assignment only after a genuine
  resolved `SUCCESS`.
- **User-impact proof:** a reviewer can see the exact moment a save becomes real (the pitch
  changes only on `SUCCESS`, verified by test: 6→7 assignments only after `resolvePending()`).
- **Accepted trade-off:** `PENDING` is a labelled fixture-simulation step (an explicit "Continue
  fixture simulation →" control), not a real network round-trip — see `BLOCKERS.md`.

## A07-S3 — permission denied

- **Current-state deficiency:** no equivalent exists to compare against — the shipped panel does
  not currently demonstrate a denial state distinctly from a generic error toast.
- **Proposed difference:** a specific denial reason, draft retained, pitch unchanged (verified by
  test: still 6 assignments, no RCM entry).
- **Accepted trade-off:** the denial is a predeclared fixture outcome, not a real authorization
  check — see `BLOCKERS.md`.

## A07-S4 — server stale/conflict

- **Current-state deficiency:** `NO_BASELINE_CAPABILITY` — no production lineup-assignment action
  exposes a revision/concurrency field today (confirmed by direct read of `lineup-actions.ts`).
- **Proposed difference:** an explicit expected/current revision and a plain-language summary,
  with no automatic merge and the draft preserved for review.
- **Accepted trade-off:** illustrative only — see `BLOCKERS.md` item 3.

## A07-S5 — planning closed after opening

- **Current-state deficiency:** no equivalent exists to compare against.
- **Proposed difference:** the editor can still be open (narrative: it was opened before the
  boundary closed) but Confirm returns an authoritative refusal, draft preserved, no fake
  force-save control anywhere.
- **Accepted trade-off:** none specific to this case.

## A07-S6 — dirty draft close

- **Current-state deficiency:** no equivalent exists to compare against.
- **Proposed difference:** closing (X, Escape, or the simulated-Back control) with an unsaved
  draft shows an explicit discard/continue prompt instead of silently losing the edit; closing with
  no draft is immediate, no prompt (verified by test, both paths).
- **Accepted trade-off:** the "browser Back" trigger is a second explicit button, not real history
  interception — see `BLOCKERS.md` item 4.

## Cross-cutting proof (all six scenarios)

A real bug was found and fixed while building this candidate: every scenario's close handler
originally discarded the draft only visually, not from the underlying state (see
`CURRENT_STATE_AUDIT.md` "Real bugs found and fixed" #1) — the dirty-draft-close scenario's own
test caught this before it could ship as a silent defect in this candidate itself.
